0. 문서 관리 규칙

원본·버전 만들기·생성·검사

  • 원본: report/editions.json(버전 기록)과 report/meta.json, 생성기 scripts/gen-report.mjs. 버전 기록의 숫자는 버전을 만들 때 기계가 잰 값이고, 사람이 쓰는 것은 버전마다의 소견(note)뿐이다.
  • 버전 만들기: npm run docs:spec이 명세를 만든 뒤 명세 버전이 직전 TR 버전과 다르면 시험을 돌리고 버전을 하나 더한다. 명세가 그대로여도 버전을 만들려면 npm run docs:report -- --force.
  • 생성: HTML은 버전 기록만으로 그린다. 그래서 같은 버전 기록이면 언제 만들어도 같은 HTML이다 — 지난 버전의 숫자를 지금 다시 재지 않는다.
  • 검사: npm test가 HTML이 버전 기록과 맞는지, 마지막 버전이 지금 명세 버전을 반영하는지 본다. 명세만 고치고 버전을 안 만들면 실패한다.

읽는 법

  • 시험 결과는 버전을 만든 그 순간 npm test와 같은 조건으로 돌린 값이다. 실패도 그대로 남긴다. 단 'TR 마지막 버전이 지금 명세 버전을 싣고 있다' 검사 1건은 그 버전을 만드는 중이라 건너뜀으로 잡힌다.
  • 기준 커밋은 버전을 만들 때의 HEAD다. 명세를 고치고 커밋하기 전에 만드는 경우가 많아, 그때는 '커밋 전 변경 있음'을 함께 적는다.
  • 행동 평가는 실제 모델을 불러 돈이 들기 때문에 버전마다 다시 돌리지 않는다. 버전에는 그때까지의 마지막 평가 결과가 실린다.
  • 로그 감사의 후보 수는 버전마다 지금 로그로 다시 센다. 확정 수는 사람이 판정한 값이라, 판정 범위 이후의 후보는 '판정 대기'로 따로 센다.

배포·보관

  • 커밋: 버전 기록과 HTML을 명세와 함께 커밋한다. 지난 버전은 지우지 않는다.
  • 공개: 명세와 같은 경로로 운영 정보를 가린 사본이 QA-Justice/tiatya-bridge-docs의 tr.html로 PR에 실린다. 머지는 사람이 한다.

5. 행동 평가

왜 하나

#build는 웹 Claude·GPT에서 한 설계 대화의 정리본을 붙여넣으면 프로젝트 문서(Log.md·Decisions.md)에 남기는 채널이다. 2026-09-05에 붙인 정리본의 "다음" 9개 중 8개는 사용자가 말한 적 없이 웹 AI가 보탠 제안이었다. 이게 사용자의 할 일로 문서에 적히면, 그 문서에서 뽑아 다음 웹 세션 첫 줄에 넣는 ○○ 컨텍스트가 정한 적 없는 일을 정해진 일로 넘긴다. 그래서 보탠 항목이 확정된 할 일처럼 저장되는지를 본다.

어떻게 하나

그날 붙인 원문을 요청 로그에 남은 그대로 다시 넣는다. 운영 볼트를 건드리지 않게 회차마다 볼트를 임시 폴더로 복사하고, 그 프로젝트를 9/5 직전 상태로 되돌린 뒤 정답이 남아 있는 곳(요청 로그, 그날의 Log 줄)을 지운다. 항목마다 누가 말했는지는 정답표 eval/build-next-items/ground-truth.json에 적어 두었다. 모델 응답은 매번 달라서 같은 코드로 3회씩 돌린다(하네스 점검용 예비 실행만 1회).

어떻게 판정하나

모델의 답변이 아니라 실행 전후 파일 차이로 본다. 새로 생긴 줄에서 항목을 찾고, 그 줄이나 그 줄이 속한 구역 머리에 미확인·제안 표시가 있는지 본다. 답변에서 출처를 되묻는지는 보조로만 센다. 항목은 정규식으로 찾아서, 모델이 바꿔 말하면 놓칠 수 있다.
